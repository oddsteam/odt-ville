# Task: No 1-tile-wide terrain strip in the generated map

**Status:** TODO
**Area:** Map generation — `frontend/src/game/constants.js` (`buildTown` / `tileFor`)
**Type:** Map-layout invariant (+ verification across map sizes)

## Invariant

> A cell of an **autotiled terrain** must never border a **different** terrain on
> two **opposite** orthogonal sides (N+S or E+W) — because the 3×3 edge set can't
> represent a "bordered on both sides" tile, so the two opposite edge tiles
> overlap into a solid fill and the transition is lost (the "solid green grass
> strip" bug). Equivalently: **no 1-tile-wide strip of one terrain wedged between
> two different terrains.**

"Autotiled terrain" = any terrain that renders with transparent edge/corner tiles
(currently grass and dirt; see `buildEdgeMap` / the catalog).

## Why this matters for a procedural map

The map is generated by `buildTown(plotCount)` and changes shape with house count
(`numRows`, `cols`, field bounds, gate position all derive from it). A fix
expressed as coordinates only holds for one `plotCount`. This invariant must hold
for **every** `plotCount`, so it belongs in the generator + a scan, not a one-off
tweak.

## Current state

- `tileFor(x, y)` in `buildTown` emits the char grid: `.`/`*` grass, `:` road,
  `g` dirt field, `T` tree (grass-type), `s` sign.
- The known trigger was the side-avenue road (`x===1`) sitting one tile from the
  field; fixed once by `fieldLeft = 4` (commit), then the field was deliberately
  enlarged to `fieldLeft = 3` again, which re-introduces the strip at column C
  (x2). So the invariant is currently **violated** by design and unguarded.
- We have a working verification recipe: a Python/JS reimplementation of
  `tileFor` that scans every cell for opposite-side different-terrain borders
  (used earlier to confirm "none — fixed").

## Requirements

1. State the invariant in code-adjacent terms (terrain types from
   `typeForTileChar`; opposite orthogonal borders).
2. **Verify across map sizes:** a test that builds the town for `plotCount`
   1..N (e.g. 1..50, covering 1..several building rows) and asserts **no** cell
   of an autotiled terrain has opposite-side different-terrain neighbours.
3. **Enforce in the generator:** choose how to guarantee it —
   - keep ≥2-tile margins between different terrains wherever a strip could form
     (avenue↔field, field↔border, stem↔field, etc.), parameterised so it holds
     as the town grows; or
   - (alternative, larger) add a "both-opposite-sides" strip tile to the autotile
     set and select it — then the invariant can relax. Pick one; default to the
     spacing approach.

## Proposed approach

1. Port the existing scan into a real test (`frontend` test runner) that imports
   `buildTown` and walks the map. Make it fail loudly on any violation, printing
   the offending cells in A1 notation + the `plotCount`.
2. Run it; for each violating `plotCount`, adjust the generator constants/bounds
   (e.g. avenue offset, `fieldLeft/Right`, margins) until the scan is green for
   the whole range.
3. Keep the test in CI so future `buildTown` edits can't silently re-introduce a
   strip.

## Acceptance criteria

- [ ] Test asserts the invariant for `plotCount` 1..N and passes.
- [ ] No `plotCount` in range produces a 1-wide strip (grass or dirt) between two
      different terrains.
- [ ] Violations (if any reappear) print offending cells + map size, not a vague
      failure.
- [ ] No rendering code changes required (this is purely about the char grid).

## Out of scope

- Adding the "both-sides strip" autotile tile (that's the alternative fix; note
  it but don't build it unless we choose that route).
- Anything about what transparent edges reveal (see the layer-hole task).

## Notes

- The minimal precise check is "opposite-side different-terrain borders", which
  is stricter and cheaper than literally measuring strip width, and it's what
  actually breaks rendering.
